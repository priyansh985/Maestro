## 1. What this repository is

A clean-room reproduction of **arXiv:2508.10043** ("Securing Agentic AI: Threat
Modeling and Risk Analysis for Network Monitoring Agentic AI System") that grew
into a **deterministic security control plane for agentic AI**. Its one sentence:

> *An LLM proposes intentions; deterministic services authorize, execute, verify,
> and record. There is no bypass path from model output to a real side effect.*

Discipline: offline, stdlib-only (plus FastAPI), deterministic, fully tested, and
**honestly graded** — the `audit_invariants()` guard fails the build on
overstatement.

## 3. Where side effects happen (the answer BP0 must give)

There is exactly **one consequential boundary**: operational tool execution
(`SEB-01`, `default_tool_adapters`). Every path to it crosses the trust spine —
perimeter → reasoner → typed proposal → policy gate → executor → ledger (see
[`trust_boundaries.md`](trust_boundaries.md), TB1–TB6). The other seven boundaries
are internal state (ledger, memory, capabilities), external network (provider
HTTP, off the default loop), or host environment (experiment replay, file writes —
**not reachable from an agent action**). Classes are defined in
[`side_effect_classes.md`](side_effect_classes.md).

**No model output reaches `SEB-01` except through a typed, authorized,
allow-listed proposal.** This is the claim the whole repo exists to make true, and
it is `verified` (adversarially bypass-tested: CTRL-L3-02).

## 4. Which controls are real

Classification is defined in [`control_status_taxonomy.md`](control_status_taxonomy.md)
(the five-rung ladder: declared → implemented → enforced → tested → verified) and
the gaps are enumerated in [`control_gap_report.md`](control_gap_report.md). The
honest headline: **15 controls gate a real side effect on the live loop**; 1 is
catalogue-only; the rest are built and non-optional but front-door or component
controls. **BP3.1** moved CTRL-L4-03 `declared → verified`: the API front door
(TB0) now requires a signed bearer token + role and is tenant-confined,
fail-closed. **BP3.2** extended that same boundary over the model-testing/
connectors API (previously `auth=NONE`) so **0 `/api` endpoints are
unauthenticated**, and added CTRL-L4-07 — a deterministic per-principal
token-bucket rate limiter (fail-closed 429). **BP3.3** added CTRL-L4-08 —
**structural multi-tenant isolation**: each principal is routed to its own
per-tenant `AgentPlatform`+ledger+memory, so one tenant physically cannot read or
reset another's state via any route (proven adversarially). None of these three
is `boundary_enforced`: they gate the front door / data partition (TB0/TB8), not
the PEP execution boundary.

**BP4** hardened the side-effect boundary itself (TB5), adding **two**
`boundary_enforced` controls (10 → 12). Every authorized action now runs inside
an in-process **executor sandbox** (CTRL-L3-04, `verified`): the adapter result
is scope-confined — it may not claim a `target` outside the authorized proposal —
and byte-bounded, so a compromised or buggy adapter fails closed rather than
smuggling an out-of-scope effect or an oversized payload past the executor. And
the executor now runs every side effect as a **durable, journaled, exactly-once**
activity (CTRL-L4-05, `implemented → tested`, now on the live loop): a
crash-and-retry replays the recorded result instead of re-executing the
mitigation — proven with a file-backed journal across a simulated restart. The
honest limit is stated at each rung: this is in-process confinement, not
kernel-level isolation, and the durable journal is the in-repo engine, not
Temporal.io — OS sandboxing (gVisor/Firecracker) and Temporal remain documented
seams.

**BP7** moved the evaluation stack onto the same boundary (12 → 14
`boundary_enforced`). A **pre-execution critique gate** now runs the HMDC engine
(blueprint §5) + a deterministic **environmental verifier** (§5.3) as the last
check before every side effect. **CTRL-L5-08** (`implemented → verified`): the
`NetworkMitigationVerifier` checks the proposed mitigation against a fixed policy
matrix keyed by the *observed* alert class — without consulting the model — and
vetoes anything inappropriate/unsafe (raising detection thresholds during a DoS,
which would blind the detector; or acting on a benign baseline) at the executor,
even though capability, risk, budget and breaker all pass. **CTRL-L5-06**
(`implemented → tested`): the full HMDC pipeline gates the loop — its
deterministic stages (dispositive guardrails, so a justification that leaks a
secret is rejected before execution; and the environmental verifier) deny
autonomously, while a probabilistic-judge disagreement *routes to a human*
rather than silently allowing or autonomously denying on a stand-in score. The
honest limit: the judge/embedder are offline lexical stand-ins, so the operative
hard gate is the guardrail + verifier pair and the engine's *contract*
(cross-family, variance-aware, route-uncertainty-to-human) is what is enforced —
a connector-backed cross-family judge is the seam that would tighten the
probabilistic thresholds.

**BP-gov** moved governance onto the same boundary (14 → 15 `boundary_enforced`)
and closed the last-but-one `declared` gap. **CTRL-L6-03** (`declared → verified`):
the executor's effective intent allow-list is no longer static code but a
**signed, versioned, content-addressed policy bundle**. A change to it requires a
**two-person rule** — the actor who *proposes* a new version may not be the one
who *approves* it — and activation HMAC-signs the bundle and records the change
(version, proposer, approvers, digest — never a secret) in the tamper-evident
ledger. Genesis (v1) is the deploy-time baseline (single-authority bootstrap,
signed but not itself a ledger event); every later version goes through
propose → approve → activate with a chained `parent_digest`. The active bundle's
signature is **re-verified at the side-effect boundary before every action**: a
tampered/absent bundle, or an intent the active policy does not permit, fails
closed (`deny 'policy_bundle'`). Adversarially tested (proposer self-approval and
duplicate-approval rejected, a stale concurrent change rejected, a forged
signature / mutated content / wrong key all fail closed, and a two-person-approved
tightening denies the de-listed mitigation on the *live* loop) — hence `verified`.
The honest limit: this uses one shared HMAC key; production would bind a distinct
signer identity (OIDC/KMS key + change-ticket) per approver.

> **The rule that keeps this honest:** a control is never marked `enforced` unless
> it is reachable on the main execution path, cannot be bypassed by a known path,
> and a negative test proves it blocks the forbidden behavior. `default-off is not
> enforcement.`

## 5. Disposition — build in place, not greenfield

Decision this session: adopt the BP0–BP13 framework as a **gap map** and build
**in place**. The working, tested core is not demoted to `legacy/`; each package
is mapped to the BP part it realizes with a disposition of KEEP / HARDEN / GAP in
[`module_disposition.json`](module_disposition.json). Summary:

- **KEEP** (realized + tested): `security`, `platform`, `connectors`, `domains`,
  `maestro`, `experiments`, `scripts`.
- **HARDEN** (present, real gap named): `memory` (Postgres RLS), `orchestration`
  (Temporal default), `critique` (wire to live gate), `server` (auth/RBAC),
  `agent` (legacy paths), `telemetry` (SOC integrity).
- **GAP** (net-new): verticals (BP8/BP9), runner (BP10), console/SDK (BP11),
  enterprise (BP13).

## 8. Stop conditions (carried forward)

Halt and remediate immediately if any of these become true — each contradicts the
one claim in §1:

1. A tool call reaches `SEB-01` without crossing TB3 (typed parse) and TB4
   (policy gate).
2. A policy check exists only in the planner/reasoner, not at the executor.
3. A control is marked `enforced` without a passing negative test (the
   `audit_invariants()` guard should already fail the build).
4. External content is promoted to `TRUSTED` memory without an independent
   capability (TB7).
5. A new `SIMULATED_EXTERNAL` / `EXTERNAL_NETWORK` / `HOST_ENVIRONMENT` boundary
   becomes reachable from a model proposal without an entry in
   `side_effect_boundaries.json` and a gating control.
6. A tenant-isolation test fails, or a retry duplicates a side effect
   (idempotency), or a secret appears in a log / decision card / ledger entry.
